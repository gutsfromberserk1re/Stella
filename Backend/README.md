# Stella Rust backend

The native raylib interface talks to the Rust `pluto-backend` C ABI DLL. There is no Tauri or WebView in the application.

## Modules

- `timeline-core/` owns clip data, validation, snapping, and timeline mutations.
- `backend-ffi/` exports a narrow C ABI. Cheap timeline commands are synchronous; media jobs, preview decoding, and proxies use separate background workers and are collected with `pluto_backend_poll` so rendering stays responsive.
- `Frontend/backend_bridge.h` loads the DLL dynamically. GitHub Actions builds the C UI and Rust DLL together and publishes a lightweight artifact plus a full FFmpeg-bundled artifact.

The FFI accepts and returns UTF-8 JSON strings. Strings returned by the backend must be released with `pluto_backend_free`. See the exported function signatures in `Frontend/backend_bridge.h` and `Backend/backend-ffi/src/lib.rs`.

## Implemented engine paths

- Timeline get/add/move/split/delete, snapping, undo/redo, clip properties, and keyframe storage run synchronously in Rust.
- Media import/inspection, thumbnail and waveform generation, proxy creation, and final export remain offline/background media jobs. Low-resolution 320×180 media thumbnails are decoded in-process through the same FFmpeg libraries and written to a small BMP cache, so they do not require `ffmpeg.exe`. Waveform generation, video metadata inspection, proxy creation, audio filtering, encoding, and muxing still use the FFmpeg command-line tools; the WGPU visual export path does not launch FFmpeg visual filter graphs.
- Preview and export source decoding use `ffmpeg-next` against the decode-only static FFmpeg libraries. Video clips keep independent sequential decoder contexts per timeline clip; still-image clips are decoded once and cached for the lifetime of their working set. Decoded RGBA frames are shared in a bounded LRU by media path, source frame, and output width, so duplicate requests avoid redundant decoding. There is no per-frame `ffprobe` or `ffmpeg` process launch on the WGPU visual path. Manual pixel conversion covers common 8-bit RGB/BGRA, planar 4:2:0/4:2:2/4:4:4, 9/10/12/16-bit little-endian planar YUV, and P010LE; unusual formats and source colorimetry/HDR handling still need further validation.
- Preview requests carry an immutable `Arc<Timeline>` snapshot created when the timeline changes. The UI does not serialize or clone the project timeline for every playback frame.
- Decoded frames are uploaded into persistent wgpu textures. The WGSL compositor uses per-layer uniforms for position, scale, rotation, crop, opacity, exposure/brightness, contrast, saturation, vibrance, HSL selection, temperature, shadows/midtones/highlights color wheels, presets, and visual effects/transitions. Multiple active video tracks are composited bottom-to-top. Preview and export call the same `LayerUniforms` mapping and WGPU compositor; export does not rebuild visual effects as FFmpeg filters.
- Windows preview presentation now attempts a WGL shared-texture path: WGPU's GLES backend renders directly into a WGPU-owned `GL_TEXTURE_2D` in the Raylib context's WGL share group. The UI samples that same texture; it does not map WGPU pixels to CPU memory or upload a second OpenGL texture on this path. Producer GLsync is used only when the UI context can see it (`glIsSync`); otherwise WGPU finishes its own context before the same texture is sampled. If context sharing is unavailable or fails on the active driver/pixel format, preview falls back to the asynchronous readback and Raylib upload path. Non-Windows builds continue to use readback. Final export still reads composited RGBA frames back to CPU memory for FFmpeg encoding.
- Preview playback accepts the newest completed frame in the current travel direction and no longer applies the previous arbitrary 200ms stale-frame rejection gate. Two backend workers accept a bounded three-request window, with request-ID keyed completion so out-of-order frames do not overwrite newer results. Windows uses the shared-texture presenter when WGL initialization succeeds; all other cases use asynchronous readback. The decoder maintains short per-clip look-ahead queues during playback.
- Preview and final export use WGPU as the sole visual renderer for every video and still-image layer. The same `LayerUniforms` mapping, shader, compositing order and transition evaluation are used in both paths. Preview renders at the selected preview resolution; export renders at the requested output resolution. FFmpeg receives the final composited RGBA frames and is used for audio filtering/mixing, video encoding and final muxing only. Unsupported visual sources fail clearly; neither preview nor export silently switches to FFmpeg video filters.

The Windows build links the in-process decoder against the LGPL-2.1-or-later decode-only static FFmpeg libraries. `ffmpeg-next`/`ffmpeg-sys-next` generate bindings during the build, so CI installs LLVM/libclang and sets `FFMPEG_DIR`. The full package may also include the separate GPL FFmpeg CLI binaries for import/proxy/export workflows; their license notices are distributed separately. The lite package includes the backend DLL and icons. Image thumbnails can be generated in-process; video import/metadata inspection and operations such as waveform/proxy generation and export still need the `ffmpeg/` folder or FFmpeg on `PATH`.

## Shared WGPU preview and export compositing

The renderer caches source textures, uniform buffers, bind groups and the render target. It composites active clips on video tracks V1 through V6 in bottom-to-top order. Source frames are decoded in-process; all visual processing after decode is shader-side. Color and transform properties update the shared `LayerUniforms`, so preview and export use the same property mapping and WGSL shader for video and still images. On Windows, the preview now uses a shared WGL texture ring when compatible contexts can join the same share group. Each frame is rendered into a WGPU texture that Raylib samples directly after a runtime-checked producer handoff. A driver-visible GLsync uses a GPU-side wait; otherwise WGPU finishes its producer context. Raylib returns a post-draw GLsync when WGPU can see it; otherwise it calls `glFinish` before returning the slot. The CPU readback path is retained as a compatibility fallback and for non-Windows platforms. Export still reads WGPU output back to CPU memory before feeding FFmpeg's encoder, so export is not zero-copy or fully optimized. Stable per-layer source slots, GPU timestamp queries, and GPU-native hardware-encoder interop remain separate milestones.

FFmpeg command-line tools resolve from `PLUTO_FFMPEG_DIR`, the app's adjacent `ffmpeg/` folder, or `PATH` for video metadata inspection, waveform, proxy, and export tasks. `Stella-Windows-x64-lite` contains `Stella.exe`, `pluto_backend.dll`, and icons. `Stella-Windows-x64-full` also contains FFmpeg/FFprobe, their shared runtime DLLs, and notices. The lightweight build can use the `ffmpeg/` folder from an earlier full download by placing it beside `Stella.exe`.

A transition is stored on the outgoing clip at `props.transitionOut` with a type and duration; it is used only when a neighboring video clip follows directly on the same track. Both native preview and export overlap the incoming clip by that duration and evaluate the transition mask on the same GPU shader.

Timeline scrubbing and left/right frame stepping use the current timeline frame-rate setting. The current preview decoder, cache, color and transform shader paths still need a Windows CI build and runtime verification against representative H.264, HEVC 10-bit, ProRes and AV1 media.

## Windows WGPU/OpenGL shared-texture preview

The Windows preview first tries a true shared-object path between WGPU's GLES/WGL context and Raylib's existing WGL context. Before the first preview request, the frontend passes its current `HGLRC` and `HDC` to the backend. The pinned WGPU HAL uses the host DC's pixel format and passes the host HGLRC as the share context when it creates WGPU's WGL context, before allocating WGPU resources. WGPU composites into a shared `GL_TEXTURE_2D`; the producer fence is runtime-probed with `glIsSync`, and a WGPU-context finish is used when the driver does not expose it to Raylib. Raylib returns a post-draw GLsync when the WGPU context can see it; otherwise Raylib calls `glFinish` before returning the texture slot across the three-texture ring.

The small WGL accessor is applied to the pinned WGPU 0.19.4 source by `Backend/scripts/prepare-wgpu-gl-share.ps1`. The script path-patches `wgpu-core`, `wgpu-hal`, and `wgpu-types` together so Rust does not compile duplicate WGPU type definitions from both local path and crates.io sources. GitHub Actions runs this script automatically. For a local Windows Cargo build, run it once from the repository root before building:

```powershell
./Backend/scripts/prepare-wgpu-gl-share.ps1
cargo build --release --manifest-path Backend/Cargo.toml -p pluto-backend-ffi
```

The script checks out the pinned upstream `v0.19.4` source into the ignored `Backend/.interop/` directory and writes an ignored root `.cargo/config.toml` patch for the entire core/HAL/types crate family. It also makes the `cfg_aliases` build dependencies standalone in both `wgpu-core` and `wgpu-hal`. It does not modify the public application ABI. The backend forwards Raylib's current WGL device context so the hidden WGPU window can request the same pixel format and is placed on the same display before context creation. The frontend verifies texture-name visibility and disables interop for the remainder of the run if the driver did not form the expected share group. Set `STELLA_DISABLE_WGPU_GL_INTEROP=1` to force the readback fallback. WGL sharing can still fail when the windows resolve to incompatible display devices or the driver rejects the share group; in that case the backend logs the reason and uses the asynchronous CPU readback fallback. The zero-copy claim applies only to the WGPU-composited preview output on a successful Windows share group. Decoded source frames are still uploaded into WGPU textures, and final export still reads the composite back for FFmpeg encoding.
